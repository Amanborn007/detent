# evals/calibration — judge calibration anchors

A judge-graded rubric only means what it claims to mean if it agrees with a
human on a handful of unambiguous examples first. This directory is the
committed calibration contract for that agreement, one subdirectory per
graded **dimension** (a quality axis a rubric can score, e.g.
`output-slop`).

## Convention

```
evals/calibration/
  <dimension>/
    anchors.json     # the RYG anchor set for this dimension
```

### `anchors.json` schema

```json
{
  "schema": "detent-eval-anchors-v1",
  "dimension": "<dimension-name>",
  "scenario": "<optional: one paragraph, the FIXED input scenario all anchors respond to>",
  "bands": {
    "green": [0.75, 1],
    "yellow": [0.4, 0.75],
    "red": [0, 0.4]
  },
  "anchors": [
    { "label": "green" | "yellow" | "red", "sample": "<hand-authored example>", "expected_range": [<lo>, <hi>], "why": "<optional: one sentence naming what earns/costs the band>" }
  ]
}
```

- `bands` are the score ranges a human would call green/yellow/red for this
  dimension; `green.lo` >= `yellow.hi` >= `red.hi` (ordering must hold, no
  gaps reversed).
- `anchors` is at least one hand-authored sample per band (three minimum:
  one green, one yellow, one red), each with an `expected_range` inside
  `[0, 1]` and inside (or consistent with) its band.
- `scenario` (optional, top-level): the one fixed input all anchors AND the
  case's graded fixture respond to — this is what makes anchor-comparison
  scoring stable across judge-model versions: the judge ranks the fixture
  against three fixed alternatives answering the same prompt, rather than
  scoring on an absolute 0..1 scale with nothing to anchor against.
- `why` (optional, per anchor): one sentence naming what earns or costs that
  band — read by a human auditing the anchor set, and quoted verbatim into
  the injected prompt block (see "Loading" below).
- Both `scenario` and `why`, when present, must be non-empty strings — the
  `calibration-anchors-valid` deterministic check enforces this (unknown
  fields are otherwise ignored by design; these two are the exceptions).
- Samples are authored by hand, not generated by a model being calibrated
  against them — an anchor a judge grades correctly by construction is not a
  calibration check.

## Loading — mechanical injection, not hand-quoted prose

`engine/eval/graders/judge.mjs` exports `loadAnchors(detentRoot, dimension)`
(reads + shape-validates `anchors.json`, hard-throwing on anything wrong —
never `{recorded:false}`, since a bad anchors reference is a case-spec bug,
not a degradation) and `formatAnchorsBlock(doc)` (a pure, deterministic
prompt block: the scenario, then one line per anchor quoting its sample and
`why` verbatim). A judge case spec opts in with `"anchors": "<dimension>"`;
`engine/eval/eval.mjs`'s `resolveJudgeCase` appends the formatted block to
the prompt automatically. This is what closed the "Rubric↔anchor drift" gap
below — a rubric no longer hand-quotes its dimension's anchors; it just
declares `anchors: "<dimension>"` and the injection keeps the two in sync by
construction. `classifyBand(score, bands)` then maps the judge's recorded
score to `"green"|"yellow"|"red"|null` (lo-inclusive/hi-exclusive, green's
`hi=1` inclusive; `null`, never a nearest-guess, for a score in a gap between
non-contiguous bands) — this is what feeds each judge case's `band` in
`engine eval`'s result JSON and human report.

## Dimensions in this repo

- `output-slop` — scribe (and herald) reader-facing prose; the original
  dimension, `evals/cases/scribe/case-scribe-slop-1.json`.
- `clerk` — ticket-drafting quality (`evals/cases/clerk/case-clerk-j2.json`).
- `scout` — research-brief quality (`evals/cases/scout/case-scout-j2.json`).
- `referee` — review-findings quality (`evals/cases/referee/case-referee-j2.json`).

Each of these J2 cases grades a static, hand-authored FIXTURE OUTPUT for the
dimension's fixed `scenario` — distinct from that skill's J1 case, which
grades the skill's own `SKILL.md` prose (doc quality, not output quality).

## Anchors are the judge's calibration contract

**Judge cases mechanically inject their dimension's anchors** via
`"anchors": "<dimension>"` on the case spec (see "Loading" above) — the
rubric itself no longer hand-quotes the anchor samples, so the rubric and
the anchor set can never silently drift apart in prose (this closes the
"Rubric↔anchor drift detection" item that used to live in "Deferred" below).

`engine/eval`'s `calibration-anchors-valid` deterministic check (see
`engine/eval/graders/deterministic.mjs`) walks every `evals/calibration/*/`
directory and asserts the schema shape above holds (now including `scenario`/
`why` when present) — this keeps the convention itself honest even in
`--no-judge` CI, where no judge ever runs to notice a broken anchor set.

## Deferred

- **`engine eval --calibrate` mode** — actually running the judge against
  each anchor and asserting it lands its `expected_range` (and, ideally, that
  its ordering across anchors matches the RYG bands) is explicitly out of
  scope for now. `anchors.json` exists and is schema-checked, and every
  judge case that opts in gets it injected mechanically; nothing yet drives
  the judge against the anchors THEMSELVES to self-check calibration.
